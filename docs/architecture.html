=^.^= GitCat architecture

GitCat turns a sentence into git/gh commands without letting the model write commands. The model only chooses operation ids from a fixed catalog of ~95 ops and fills in their arguments; code builds the argv, classifies risk, runs it, and handles failures. That keeps a 4B local model at 96% plan accuracy with ~0.9 s per plan.

Components

Router

Exact phrases (push, status), raw git …, cd … → steps with zero model calls. src/agent/router.js

Planner

One model call → {reply, steps, ask, explain}. Every step validated against the catalog; one repair round. agent.js askModel()

Catalog

Ops with typed params, risk tier and build() → argv. The "boilerplate". src/catalog/

Executor

Confirm policy (mode × risk), re-snapshot between steps, auto commit messages. agent.js execute()

Intent guard

Your words correct risky parameters the model got wrong (merge direction, ours/theirs, --hard, public). Vague "delete it" becomes a question. intent.js

Verifier

After each change, checks the real state (ls-remote, gh --json). "Done" only when verified; never on exit code alone. verify.js

Debugger

Known-error table first (instant), model diagnosis second; fixes always confirmed; max 2 rounds. knownErrors.js

TUI

Ink: static transcript, animated cat + status, prompt with slash menu and history, confirm box. src/ui/App.js

One request, end to end

flowchart TD
  U[user types a request] --> S[snapshot repo: status, branches, remotes, stashes, gh accounts]
  S --> R{fast path match?}
  R -- "status / push / git log -3" --> X
  R -- no --> P[model: pick ops from catalog + args]
  P --> V{valid ops and args?}
  V -- no --> P2[one repair round with the exact error] --> X
  V -- yes --> G[intent guard: user's words fix parameters] --> X[build argv per step]
  X --> C{needs confirm? mode × risk}
  C -- declined --> E[nothing runs]
  C -- ok --> RUN[run step, re-snapshot before next]
  RUN -- fails --> K{known error?}
  K -- yes --> F[fix plan, e.g. pull --rebase then push]
  K -- no --> D[model diagnosis + fix plan]
  F --> C2[confirm fix] --> RUN
  D --> C2
  RUN -- ok, explain=true --> A[model summarizes output]

The surprising step: commands are built at run time, not plan time. push after branch_create must see the new branch to add -u origin <branch>, so the executor re-snapshots between steps. Skip that and the second step pushes the old branch.

How a change ships

flowchart LR
  E[edit src/] --> T[npm test — 74 tests]
  T --> EV[node scripts/eval.js ollama — accuracy must not drop]
  EV --> E2[node scripts/journey.js — 73 real-user prompts, 0 lies]
  E2 --> D[python check_docs.py --write]
  D --> C[commit]

scripts/eval.js is what catches prompt regressions: one catalog-description change moved local accuracy from 90% to 96%; a JSON-schema change dropped it to 70%.
